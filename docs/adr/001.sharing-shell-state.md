# ADR-001: Sharing state between micro-frontends

Nov 4, 2026 · @Ruslan Lukianenko

## Problem

**Status:** Needs review

The portal is split into micro-frontends (MF) with Module Federation. The shell loads App Hub, App Hub loads CAD, and the shell knows nothing about CAD. All remotes render inside one React tree with one React instance (spike: AC-2, AC-7).

State that crosses MF boundaries:

| State | Owner | Read by | Written by |
| --- | --- | --- | --- |
| Auth: user, roles, sign-out | shell | all MFs | shell |
| Layout: breadcrumbs, header slot | shell | shell | all MFs, through actions |
| Notifications: toasts | shell | shell | all MFs, through actions |
| Runtime config | shell | all MFs | shell |
| Server data | one shared QueryClient | each MF, own queries | each MF |

Module-local state, such as CAD filters, stays inside its module and is not shared.

Each MF is built as its own bundle. If React or a context ends up in more than one bundle, the page gets several instances, for example a second context object. A remote then reads an empty context instead of the shell's one. The UI looks fine, but the remote sees no user or shows stale state. Often nothing reports an error, so these bugs are hard to find. We must have exactly one instance of React and of each context on the page (see Appendix A and Appendix C).

We need one simple way to share this state. It must work at any depth (shell → App Hub → CAD, shell → CAD), in both directions, and without new libraries.

## Options

Option 1 is chosen: it uses only the current stack and fails loudly on a breaking change.

### 1. Contracts package (chosen)

Contexts and hooks live in `@portal/contracts`, shared by Module Federation as a singleton. The shell renders the providers.

**Pros**

- No new libraries.
- One context object for the whole page.
- Types come from the same package.
- A breaking change fails loudly through `strictVersion` (see Appendix A).

**Cons**

- We must track which versions of the package are published and which version each MF requires.
- The shell must deploy before remotes that need a newer version (see Appendix B).

### 2. Expose contexts from the shell

The shell exposes `./contracts`. Remotes import `shell/contracts` as a remote module.

**Pros**

- Remotes always get the shell's version. No version range to manage.

**Cons**

- **Cycle between apps.** The shell loads App Hub, and App Hub loads the shell back. Every remote needs the shell URL, and a remote cannot start or be tested without a running shell.
- **Types must be shared separately.** Module Federation ships code, not TypeScript types. We would need a types package or federated types (out of scope, NFR-12), so we keep a package anyway.
- **No fail-fast.** A removed or renamed field shows up as `undefined` at runtime instead of an error.

### 3. Shared store (Zustand / Redux / Jotai)

A store library is shared as a singleton. The shell creates the store, remotes subscribe to parts of it.

**Pros**

- Selectors give fine control over re-renders.
- State can be read outside React.

**Cons**

- A new library to pin and share, like React.
- Changes to the store shape are silent.
- Too much for the small amount of state we share.

### At a glance

|  | 1. Contracts package | 2. Expose from shell | 3. Shared store |
| --- | --- | --- | --- |
| New dependencies | None | None | Store library |
| Breaking change | Fails loudly | Silent | Silent for store shape |
| Coupling between apps | Package only | Cycle, shell URL in every remote | Package plus library |
| Types | From the package | Separate package needed | From the package |

Option 3 stays as a fallback. We move to a store only if shared state becomes large, changes often and is read in parts by many MFs, or must be read outside React.

## Decision

Share state through **React Context** defined in a separate package, `@portal/contracts`, shared by Module Federation as a singleton with a semver range.

- `@portal/contracts` holds only types, contexts and hooks. No implementation, no state.
- The shell owns every provider. Remotes only read state and call actions.
- Each domain (Auth, Layout, Notifications, Config) has its own context. State and actions live in separate contexts, so remotes that only call actions do not re-render.
- Every context has `null` as default, and every hook throws if the provider is missing (see Appendix C).
- `@portal/contracts` uses `requiredVersion: "^1.0.0"`, so patch and minor updates do not break loading. A major update fails loudly (see Appendix A).
- Server data stays in the shared QueryClient. Query keys start with the MF name, for example `['cad', 'analysis', …]`.
- `getOrCreateContext` (the `globalThis` registry) is removed (see Appendix C).

## Consequences

**Good**

- No new libraries. One pattern for all shared state.
- MFs can deploy on their own for patch and minor changes.
- Breaking changes and setup errors fail loudly and stay inside `RemoteBoundary`.
- A remote can be tested alone with mock providers.

**Bad**

- We must track which versions of `@portal/contracts` are published and which version each MF requires.
- The shell must be deployed before any remote that needs a newer minor version (see Appendix B).
- A major version means all MFs update together.
- Only additive changes are allowed in minor versions. Reviewers must check this.

## Appendix A. How sharing works

Module Federation loads one copy of `@portal/contracts` for the whole page and checks that each MF can use it.

| Option | What it does |
| --- | --- |
| `singleton: true` | Only one copy is loaded. With `shareStrategy: "loaded-first"`, the first MF to load it wins, which is the shell. |
| `requiredVersion` | The versions this MF accepts, as a semver range. |
| `strictVersion: true` | If the loaded version is outside `requiredVersion`, loading the remote throws. Without it, MF only logs a warning and uses the wrong version. |

Example `shared` block (`mf-shared.ts`):

```ts
export const shared = {
  // libraries: exact versions, updated together
  react: { singleton: true, strictVersion: true, requiredVersion: "19.0.0" },
  "react-dom": { singleton: true, strictVersion: true, requiredVersion: "19.0.0" },
  "react-router-dom": { singleton: true, strictVersion: true, requiredVersion: "6.30.4" },
  "@tanstack/react-query": { singleton: true, strictVersion: true, requiredVersion: "5.90.2" },

  // contracts: any 1.x is accepted, 2.0.0 fails loudly
  "@portal/contracts": { singleton: true, strictVersion: true, requiredVersion: "^1.0.0" },
};
```

What happens when versions differ:

| Shell provides | CAD requires | Result |
| --- | --- | --- |
| 1.2.0 | ^1.0.0 | Loads |
| 1.2.3 | ^1.2.0 | Loads |
| 1.1.0 | ^1.2.0 | Fails loudly: shell is older than CAD needs |
| 2.0.0 | ^1.0.0 | Fails loudly: breaking change |

A failed load is caught by `RemoteBoundary` (FR-16). The shell stays alive and the remote shows "Reload page".

The package must move from `0.0.1` to `1.0.0` first. In semver, `^0.0.1` matches only `0.0.1`, so the range would not help.

## Appendix B. Shipping a change to production

Minor and patch versions let each MF deploy on its own after the shell. A major version is one release for all MFs.

&#91;embedded content: contracts release flow · 2 paths\]

1. **Edit** `@portal/contracts` in a PR. The reviewer picks the version type:
   - patch: a fix, no API change;
   - minor: something added, such as a new field, hook or context;
   - major: something removed, renamed or changed in shape.
2. **Publish** the new version. Until the MF split it is a workspace package, so this is only a version bump.
3. **Deploy the shell first.** Its providers must support the new version before any remote uses it.
4. **Update remotes when they need it.** A remote raises its `requiredVersion` (for example to `^1.3.0`) only when it starts using the new API, then deploys.

Rule for `requiredVersion`: set it to the lowest version whose API the MF uses.

## Appendix C. Why we do not keep the context on window

The MF singleton already gives every MF the same context object, so a global copy adds nothing and hides errors.

- **Context identity.** A context is found by its object reference. One copy of `@portal/contracts` means one `AuthContext` for the whole page.
- **Errors stay loud.** A version mismatch throws through `strictVersion`. A second copy of the package (missing from `shared`, stale dev cache) makes `useAuth()` throw because it reads `null`. `RemoteBoundary` catches both.
- **The registry hides problems.** With `getOrCreateContext`, two copies of the package would silently work. Any future module-level code in the package would then split into two copies without warning.
- **State is not in the package.** Values and actions live in the shell providers, not in the module, so nothing else needs a global.

To find a second copy early, the package logs `[mf-check] @portal/contracts loaded twice` in dev mode (NFR-10).
